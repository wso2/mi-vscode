Flows & Sequences

How things actually happen at runtime — the six flows that cover almost everything the server does.

1 · Startup & initialization

Two-phase handshake. Init-option schema mappings are registered during initialize; workspace settings are pulled afterwards during initialized. Validation is deferred until both are in place.

Why the deferral? If a document change arrived before the workspace config was pulled, it would validate against the wrong (or no) schema. The initialConfigurationLoaded flag gates all validation until phase two completes.

2 · Document change → diagnostics

The main loop. Edits are debounced 300 ms per document, so a typing burst runs this once after the user pauses. Note both engines are touched: the completion schema is registered and the WASM validator runs. A version guard at publish time discards results that went stale while validation was running.

Step by step

  1. Debounce Each edit cancels the previous timer; validation fires 300 ms after the last keystroke. Pending timers are cancelled when the document closes.
  2. Snapshot version validateAndSend captures document.version on entry — the live document keeps advancing while async work runs.
  3. Parse The document text becomes an AST; a namespace is used only if the parsed document exposes one.
  4. Resolve SchemaAssociator picks an XSD by user/init pattern first, then by built-in namespace fallback.
  5. Register completion schema (once per document) The referenced XSD graph is loaded and registered under an auto://<path> URI so completion/hover have a model. Skipped on later edits via hasSchema().
  6. Get validator A ProjectValidator is created (or reused) for that xsdPath, fed every .xsd/.dtd in the folder.
  7. Validate Xerces runs syntax + schema validation in one SAX pass.
  8. Map & filter Raw errors → LSP ranges; noisy cascades collapsed and de-duplicated.
  9. Version guard If document.version moved on during validation, the result is discarded — a slow older run can never overwrite a newer one.
  10. Publish Diagnostics are sent; if no schema matched, any stale diagnostics are cleared.

Why the version guard? Validations for versions 5 and 6 can finish out of order — if v5's (slower) run completed after v6's, it used to overwrite the correct diagnostics with squiggles computed from text that no longer exists. The guard makes publish order irrelevant; the debounce makes the race rare in the first place.

3 · Schema resolution priority

The decision SchemaAssociator.findSchema() makes. User patterns always win over built-in namespace matches.

The red branch: a user association that matches but points at an unreadable XSD returns null rather than falling through to the built-in schema — so a single bad xsdPath in settings silently disables validation for those files. See trade-offs.

4 · Completion request

Read-only and fast — served entirely by engine ②. It prefers the rich auto:// provider built during validation; if that isn't ready yet it builds a partial one on the fly.

5 · Hover (with diagnostic suppression)

Hover is where the two engines meet. To avoid showing misleading hover content for something Xerces flagged as invalid, the handler checks the diagnostics first.

Reconciliation point: this hasErrorAt() gate is how the two engines are kept from contradicting each other in the UI — engine ① (Xerces) gets the last word over engine ② (completion model).

6 · Configuration reload

When settings change, everything schema-related is rebuilt from scratch so updated settings replace rather than accumulate on top of the old ones.

The fix this encodes: earlier code re-registered schemas on every change without clearing first, so associations piled up. Clearing then re-applying both the init-option and workspace sets (in that order) keeps resolution priority identical to a fresh startup.
